# SDK-generated assembly metadata and PolicySharp scopes

PolicySharp analyzes generated C# code. This remains important: a generator must not bypass the application's default-deny dependency policy merely by writing `// <auto-generated/>` or creating a `.g.cs` file.

.NET SDK projects also generate assembly metadata in `obj/<configuration>/<target framework>/`. Unlike application code, `[assembly: ...]` attributes do not belong to an application namespace and may produce `PSHARP2002` (missing scope) even when the user has no policy violation.

The analyzer therefore exempts **only** operations inside recognized assembly-level metadata attributes emitted to SDK-style `*.AssemblyInfo.cs` or `.*.AssemblyAttributes.cs` filenames **under `obj`**. It resolves the attribute constructor semantically and requires the type to come from a runtime assembly; file names or `auto-generated` comments alone cannot qualify. It also handles named attribute properties such as `FrameworkDisplayName`.

The exemption does not extend to:
- arbitrary generated application classes, operations, or API dependencies;
- hand-authored assembly metadata outside the SDK's `obj` tree;
- unrelated assembly attributes not on the explicit metadata allowlist;
- missing/ambiguous/invalid policy input.

This is a narrow compiler-infrastructure compatibility allowance, not a cryptographic proof that the SDK authored the file. A fully adversarial build pipeline can impersonate paths and alter analyzer execution; use trusted CI, code ownership, reviewed policy changes and independent canary builds.

Tests: `GeneratedCodePolicyTests` contains positive and negative Roslyn cases; `tests/agent_guard/verify_sdk_metadata.sh` builds a NuGet packaged consumer with default SDK generation enabled, then confirms an unapproved hand-authored assembly attribute remains denied.
